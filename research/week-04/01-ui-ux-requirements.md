# RedHawk UI/UX Requirements

## 1. Introduction

The RedHawk platform requires a clear and practical user interface because reconnaissance produces information from multiple tools and modules. The dashboard must present this information in a centralized form so that users can understand the discovered attack surface without manually reading raw command output.

The UI/UX design for RedHawk is therefore focused on simplicity, visibility of important findings, consistent navigation, and clear separation between targets, scans, assets, services, and reports.

## 2. UI/UX Objectives

The interface should:

- Provide a centralized dashboard for reconnaissance results.
- Allow users to add and manage authorized targets.
- Allow users to configure and start reconnaissance scans.
- Display scan progress and status clearly.
- Present discovered assets in structured tables/cards.
- Show services, ports, DNS records, HTTP observations, and technologies in readable formats.
- Allow users to inspect individual assets.
- Provide access to generated reports.
- Display errors without exposing sensitive backend details.
- Maintain consistent navigation and visual hierarchy.

## 3. Main Application Pages

### Dashboard

The dashboard is the primary overview page.

It should display:

- Total targets
- Total scans
- Running scans
- Completed scans
- Discovered assets
- Open services/ports
- Recent scan activity
- Recent discoveries
- Scan status summary

The dashboard should provide quick navigation to important modules.

### Target Management

The target page allows authorized targets to be registered and managed.

Required information may include:

- Target name
- Domain/hostname
- IP address when applicable
- Description
- Scope/authorization note
- Date added
- Last scan
- Current status

Actions:

- Add target
- View target
- Edit target
- Delete target
- Start scan

### Scan Interface

The scan page allows users to create a reconnaissance job.

Possible options:

- Target selection
- Reconnaissance modules
- Scan profile
- Optional configuration
- Start scan

The page should display:

- Queued
- Running
- Completed
- Failed
- Cancelled

### Assets Page

The assets page provides the discovered attack-surface inventory.

Asset types may include:

- Domains
- Subdomains
- IP addresses
- Hosts
- Web applications

Useful fields:

- Asset name
- Asset type
- Source module
- First discovered
- Last seen
- Status

### Findings/Observations Page

This page organizes observations generated by reconnaissance modules.

Examples:

- Open ports
- Detected services
- DNS records
- HTTP headers
- HTTP status codes
- Technologies
- Tool observations

### Reports Page

The reports page provides generated reconnaissance reports.

It should contain:

- Report name
- Target
- Scan ID
- Creation date
- Summary
- Report status
- Export/view action

## 4. Navigation

Recommended navigation:

Dashboard
→ Targets
→ Scans
→ Assets
→ Findings
→ Reports
→ Settings

The navigation should remain consistent across application pages.

## 5. UX Principles

RedHawk should follow:

1. Simplicity — avoid unnecessary controls.
2. Consistency — use common components and terminology.
3. Visibility — important scan and discovery information should be easy to find.
4. Feedback — show loading, success, failure, and progress states.
5. Error clarity — explain what the user can do next.
6. Accessibility — maintain readable text, labels, keyboard-friendly controls, and adequate contrast.
7. Responsiveness — pages should remain usable on different screen sizes.

## 6. Design States

Every major component should consider:

- Loading state
- Empty state
- Success state
- Error state
- Disabled state
- Running state

For example, an empty Assets page should explain that no assets have been discovered yet instead of showing a blank screen.

## 7. Week 4 Design Outcome

The UI/UX research establishes the screen structure and interaction model that can be implemented during the development phase beginning in Week 5.
